# 레거시 모듈 문서화

- 분석 대상 폴더의 파일은 읽기만 한다. 수정 · 생성 · 삭제하지 않는다.
- 문서와 답변은 한국어, 코드 식별자는 영어로 쓴다.

## 모듈명
`<모듈명>` 은 폴더 이름이 아니라 아래 셋 중 하나다.
- `legacy/item-bank-php` → `item-bank`
- `legacy/assignment-thymeleaf` → `assignment`
- `legacy/grade-mssql` → `grade`

산출물: `docs/<모듈명>/ARCHITECTURE.md` · `ERD.md` · `BUSINESS-RULES.md`

## 절차
각 단계가 끝나면 결과를 해당 파일에 저장한 뒤 다음 단계로 넘어간다. 저장 전에는 넘어가지 않는다.

1. **계획 제시**: 분석 범위(`$ARGUMENTS` 의 범위 제한 반영), 읽을 파일 목록, 단계별 산출물을 먼저 보여 준다. 코드를 읽기 전에 사용자 확인을 받는다.
2. **진입점**: 요청 · 화면 · 배치 · 프로시저 호출 지점을 찾아 `ARCHITECTURE.md` 에 저장한다.
3. **의존 관계**: 진입점에서 이어지는 호출 방향(계층 · 파일 간)을 정리해 `ARCHITECTURE.md` 에 보탠다.
4. **데이터 흐름**: 입력 → 처리 → 저장 · 응답 경로와 테이블 · 컬럼 · 키 관계를 `ERD.md`(mermaid `erDiagram`)에 저장한다. 스키마 파일에 없는 관계는 "추정"으로 표시한다.
5. **비즈니스 규칙 후보**: 분기 · 검증 · 계산 · 상태 코드에서 규칙을 뽑아 `BUSINESS-RULES.md` 에 저장한다.
6. **표본 점검 추천**: 사람이 직접 확인할 규칙 3개를 추천한다. 아래 "표본 점검"을 따른다.

## 규칙 형식
규칙마다 아래 항목을 모두 채운다.

```
### BR-01 <규칙 이름>
- ID: BR-01
- 규칙: <한 문장. 조건과 결과>
- 근거 파일:줄번호: `legacy/.../Foo.java:120-134`
- 근거 코드 인용: <해당 줄의 원문 그대로>
- 확신도: 높음 | 중간 | 낮음
- 비고: <예외 · 도달 조건 · 확인하지 못한 것>
```

- 확신도는 코드 원문으로 동작을 끝까지 따라갔으면 높음, 일부만 봤으면 중간, 추정이면 낮음이다.
- 주석 · 변수명만 근거로 삼은 규칙은 확신도를 낮음으로 쓴다.

## 하지 말 것
- 코드에 없는 함수 · 클래스 · 컬럼을 만들어 쓰지 않는다. 이름을 적기 전에 Grep 으로 존재를 확인한다.
- 호출 방향을 짐작으로 적지 않는다. "A 가 B 를 부른다"는 A 쪽 호출 줄을 찾은 뒤에만 쓴다.
- 코드에 없는 규칙을 창작하지 않는다. 화면 문구 · 주석 · 문서에만 있고 코드로 확인 못 한 것은 확신도 낮음과 비고로 남긴다.
- 스키마상 도달할 수 없는 분기를 규칙으로 적지 않는다. `NOT NULL` · FK · INNER JOIN 으로 막힌 분기(null 마감 시각, 없는 학급 경고 등)는 스키마 줄번호를 확인한 뒤 "도달 불가"로 비고에 적는다.
- 적용 범위를 뭉뚱그리지 않는다. 재배포에만 있는 정규화를 전체 배포 규칙으로 쓰거나, 분 단위 비교를 "정각"으로 쓰는 식의 오류를 낸다. 규칙마다 어느 경로에 적용되는지, 비교 단위가 무엇인지 적는다.
- 한 곳(서비스)만 보고 다른 경로(화면 · SQL · 프로시저)의 검사를 빠뜨리지 않는다. 같은 규칙이 여러 층에 있으면 층마다 줄번호를 적는다.
- 줄번호를 기억으로 적지 않는다. 인용은 방금 읽은 원문을 복사한다.

## 표본 점검
사람이 확인할 규칙 3개를 골라 ID · 이유 · 볼 파일:줄번호를 적는다.
1. 가장 그럴듯한 규칙 1개: 문장이 자연스럽고 확신도가 높아 그냥 믿기 쉬운 규칙. 그럴듯함이 검증을 건너뛰게 만든다.
2. 확신도 낮음 또는 중간인 규칙 1개.
3. 다른 규칙이나 화면 · 계산에 가장 많이 얽힌 규칙 1개.

사람이 판정하기 전에는 "검증 완료"라고 쓰지 않는다. 모델이 코드로 대조한 것은 "모델 확인"으로 구분해 적는다.

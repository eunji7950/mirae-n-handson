# 승인 체크리스트 v1

버전: v1 · 2회차 (2026-10-06)
- 네 기준의 항목을 모두 "예 / 아니오"로 답하는 문장으로 바꾸고, "충분한가 · 적절한가"를 구체 조건(새 public 서비스 메서드 · 새 엔드포인트 · 분기 추가)으로 대체했다.
- 치명 이슈를 7개 분류(비밀값 · 데이터 손실 · 노출 · 개인정보 · SQL 조립 · 장애 유발 · 보호 대상)로 확정하고, 컨벤션 위반을 반려 / 경고 / 제안 대상으로 나눴다.
- 검증 범위를 "마지막으로 승인된 커밋...HEAD" 로 고정하고, "확인 필요"는 승인 보류, 경고는 조치 또는 보류 사유 기록을 조건으로 승인 가능하게 정했다.

AI 가 만든 변경분 · 외주사 PR 을 머지하기 전에 리뷰어가 대조하는 목록이다. 네 기준이 **모두** 충족되어야 승인이다. 하나라도 미충족이면 반려.

- 각 항목은 "예"가 충족이다. 하나라도 "아니오"면 그 기준은 미충족이다(항목 끝에 경고로 표시한 것은 제외).
- 답을 정할 근거가 없으면(테스트를 실행하지 못함, 서버 빌드를 확인하지 못함 등) "확인 필요"로 적는다. "확인 필요"가 남아 있으면 승인하지 않고 **보류**한다.

## 심각도 정의

- **치명** — 아래 2절의 치명 이슈 목록에 해당하는 문제. 1건이라도 있으면 반려.
- **경고** — 지금 동작은 하지만 다음 변경에서 사고가 될 수 있는 문제. 경고가 있어도 승인할 수 있다. 단, 다음 커밋 전에 조치하거나 리뷰 기록에 "보류 사유"를 한 줄 남긴다.
- **제안** — 더 나은 방법이 있다는 의견. 승인 · 반려에 영향을 주지 않는다. 목록으로만 남긴다.

이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향 네 항목으로 적는다. 근거 줄번호를 댈 수 없는 지적은 "확인 필요"로 따로 둔다.

## 1. 테스트 통과

- [ ] 변경된 모듈의 테스트 명령을 실제로 실행했는가? (실행하지 못했으면 "확인 필요" → 보류)
- [ ] 실행 결과의 실패 · 오류가 0건인가?
- [ ] 새 public 서비스 메서드마다 테스트가 1개 이상 있는가? (getter · setter · 생성자, record 의 단순 `from()` 변환은 제외)
- [ ] 새 엔드포인트마다 `@WebMvcTest` 테스트가 1개 이상 있는가?
- [ ] 기존 메서드에 분기를 추가하거나 예외 처리를 바꿨다면, 그 분기를 지나는 테스트가 1개 이상 있는가? (아니오면 **경고**. 기준 미충족으로 보지 않는다)
- [ ] 이관 코드라면, 새 API 를 대상으로 한 characterization(`TARGET_BASE_URL=http://localhost:8080 npm test`)이 전부 통과했는가?
- [ ] 이관 코드라면, 대상 서버의 기동 시각이 마지막 변경(소스 수정 · 컴파일) 이후인가? (확인하지 못했으면 "확인 필요" → 보류)
- [ ] 기존 테스트를 지우거나 skip · `@Disabled` 를 추가한 곳이 하나도 없는가?
- [ ] `characterization/` 의 테스트 코드나 스냅샷을 고치지 않았는가?

## 2. 치명 이슈 0건

아래 질문에 모두 "아니오"여야 충족이다. "예"가 하나라도 있으면 그 건은 치명 이슈다.

- [ ] 비밀값 노출: 운영 계정 · 토큰 · 키가 코드 · 설정 · 테스트 픽스처에 리터럴로 들어 있는가? (실습 더미 `app-pass` 는 제외)
- [ ] 비밀값 노출: `.env*` 파일을 만들었거나, 운영 DB 호스트(`prod-db` 등)에 접속하는 설정 · 명령이 있는가?
- [ ] 데이터 손실: 요청에 없는 데이터 삭제 · 덮어쓰기 코드가 있는가?
- [ ] 데이터 손실: 묻지 않고 DB 스키마 · 시드(`db/`)를 바꿨는가?
- [ ] 노출 · 인증 우회: 비공개 문항(`status != 'A'`)이 응답에 나갈 수 있는가?
- [ ] 노출 · 인증 우회: `WebConfig` 의 CORS 허용 범위(`http://localhost:5173` · GET)를 넓혔는가?
- [ ] 노출 · 인증 우회: `dangerouslySetInnerHTML` 을 썼는가?
- [ ] 개인정보: 학생 식별자(`STU-…`) · 이메일 · 토큰 값을 로그에 출력하는가?
- [ ] SQL 문자열 조립: 사용자 입력을 SQL 문자열에 이어 붙이는 곳이 있는가? (파라미터 바인딩이면 해당 없음)
- [ ] 장애 유발: `@Transactional` 메서드(클래스 단위 선언 포함) 안에서 외부 HTTP 를 호출하거나 전체 테이블을 도는 루프가 있는가?
- [ ] 장애 유발: `application.yml` 의 HikariCP 설정(`maximum-pool-size: 5`, `connection-timeout: 3000`)을 바꿨는가?
- [ ] 보호 대상 수정: 허락 없이 `legacy/` 를 수정했는가?

## 3. 요청 범위 이탈 없음

- [ ] 요청 문장이 한 문장으로 확인되었는가? (아니오면 판정하지 않고 먼저 묻는다)
- [ ] 검증 범위가 "마지막으로 승인된 커밋...HEAD" 인가? (기준 커밋이 불분명하면 판정 전에 묻는다. `upstream/main` 이 뒤처져 있다고 범위를 넓히지 않는다)
- [ ] 변경 파일마다 요청 문장으로 설명되거나 아래 허용 목록에 들어가는가?
  - 변경한 파일 안의 import 정리
  - 변경한 메서드의 주석
  - 그 변경을 검증하는 테스트 파일
  - 리뷰 기록(`docs/verify/`)
- [ ] 요청과 무관한 파일이 2개 이하이고, 모두 같은 도메인 패키지 안의 오타 · 포맷 수정인가? (1~2개면 **경고**, 3개 이상이거나 다른 도메인 패키지 · 다른 모듈 문서가 섞이면 미충족)
- [ ] 의존성(`build.gradle` · `package.json`), `application.yml`, `WebConfig`, `db/` 를 바꿨다면 그 변경이 요청에 들어 있었는가?

## 4. 컨벤션 준수

- [ ] 팀 `CLAUDE.md` 와 대조했는가? (`convention-check` Skill 결과를 근거로 쓴다)
- [ ] 아래 **반려 대상**이 하나도 없는가? (하나라도 있으면 미충족)
  - 계층 규칙 위반: 컨트롤러에 Repository 주입 · SQL 문자열, 서비스에 다른 도메인의 Repository 주입
  - 컨트롤러가 엔티티를 반환
  - 빈 `catch` 블록
  - 컨트롤러 메서드 안의 try/catch
  - `System.out` · `System.err` · `printStackTrace()` · `console.log`
  - main 코드의 인자 없는 `LocalDateTime.now()` · `LocalDate.now()` · `System.currentTimeMillis()`
  - main 코드의 `@Autowired` 필드 주입 · Lombok
  - `any` · `as unknown as` · `@ts-ignore`
  - 컴포넌트 · 훅에서 `fetch` 직접 호출
- 아래는 이슈 목록에 올리지만 기준 판정에는 영향을 주지 않는다.
  - **경고**: 네이밍(`from()` 등 팩토리 이름 포함), 매직 넘버 · 상태 코드 리터럴, 맞지 않는 로그 레벨, 테스트의 `@ActiveProfiles("test")` · `@DisplayName` 누락, JSX 인라인 `style`, `getByTestId`
  - **제안**: 120자 초과, 주석 품질, 더 나은 구현 방법
- 경고 · 제안은 같은 패턴이 기존 코드에 있으면 그 `파일:줄번호` 를 근거로 한 단계 낮추거나 반박할 수 있다. 반려 대상에는 이 예외를 적용하지 않는다.

## 판정 형식

첫 줄에 `판정: 승인`, `판정: 반려`, `판정: 보류`("확인 필요"가 남아 있을 때) 중 하나를 쓴다. 이어서 네 기준의 충족 · 미충족 표, 그다음 이슈 목록(심각도 · `파일:줄번호` · 근거 · 수정 방향)과 확인 필요 목록을 쓴다. 경고를 남긴 채 승인하면 경고마다 "조치 예정" 또는 "보류 사유"를 한 줄씩 붙인다. 코드는 수정하지 않는다.

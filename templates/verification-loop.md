# AI 검증루프 v1

버전: v1 · 2회차 (2026-10-06)
- 판정 기준(6절)을 "충분한가 · 적절한가"에서 `templates/approval-checklist.md` v1 의 예 / 아니오 항목으로 바꿨다.
- 검증 범위를 "마지막으로 승인된 커밋...HEAD" 로 고정하고, 이관 코드는 대상 서버가 HEAD 로 빌드되었는지 확인하는 단계를 넣었다.
- 판정에 "보류"(확인 필요가 남은 경우)를 더하고, 경고는 조치 또는 보류 사유를 남기는 조건으로 승인할 수 있게 했다.

AI 가 만든 변경분과 외주사 PR 을 머지하기 전에 거치는 절차다. **만든 쪽과 검증하는 쪽을 분리**하고, 판정은 `templates/approval-checklist.md` 의 네 기준으로 한다.

## 1. 왜 분리하나

만든 세션은 자기 코드를 옹호한다. 같은 컨텍스트 안에서 "잘 됐는지 확인해 주세요"라고 물으면 만든 이유를 다시 설명받을 뿐이다. 검증은 **변경분만 보는 새 컨텍스트**에서 한다.

## 2. 패턴

| 패턴 | 방법 | 쓰는 때 |
|---|---|---|
| 만든 세션 → 리뷰 세션 | 새 터미널에서 Claude Code 를 새로 띄워 diff 만 보게 한다 | 기본. 모든 변경 |
| Claude 생성 → 다른 모델 리뷰 | 새 터미널에서 `claude --model sonnet` 처럼 다른 모델로 새 세션을 띄워 같은 diff 와 체크리스트를 넘긴다 | 중요한 변경의 교차 검증 |
| 리뷰어 Sub-agent | 읽기 전용 리뷰어를 `.claude/agents/` 에 정의해 두고 위임한다 | 같은 세션 안에서 격리된 컨텍스트로 리뷰할 때 |

## 3. 역할

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 만든 세션 | 구현, 테스트 작성, 리뷰 결과 반영 | 자기 변경의 승인 판정 |
| 리뷰 세션 | diff 읽기, 체크리스트 대조, 테스트 실행, 이슈 목록과 판정 | **코드 수정.** 고치기 시작하면 그 순간 "만든 쪽"이 된다 |
| 사람 | 요청 범위 확정, 리뷰 이슈의 수용 · 기각, 최종 머지 | 리뷰어의 판정을 읽지 않고 머지 |

## 4. 절차

1. **요청 범위 확인.** 무엇을 요청했는지 한 문장으로 받는다. 범위가 주어지지 않았으면 판정하지 말고 먼저 묻는다.
2. **변경 파일 목록과 diff 읽기.** 범위는 `git diff --stat <마지막으로 승인된 커밋>...HEAD` 다. 기준 커밋이 불분명하면 판정하기 전에 묻는다(`upstream/main` 이 뒤처져 있다고 범위를 넓히지 않는다). 목록을 먼저 보고, 파일마다 diff 를 읽는다. patch 파일이면 `git apply --stat` 으로 목록을 뽑는다.
3. **체크리스트 대조.** `templates/approval-checklist.md` 를 읽고 항목마다 충족 · 미충족 · 확인 필요 중 하나로 표시한다.
4. **테스트 실행.** 변경된 모듈의 테스트만 실행한다. 어느 명령을 쓰는지는 팀 `CLAUDE.md` 의 빌드 · 테스트 명령을 따른다. 결과는 통과 · 실패 수와 실패한 테스트 이름만 남기고 전체 로그를 대화에 싣지 않는다. 이관 코드는 characterization 을 새 API(`TARGET_BASE_URL=http://localhost:8080`) 대상으로 돌리기 전에, 대상 서버의 기동 시각이 마지막 변경(소스 수정 · 컴파일) 이후인지 확인한다(예: `ps -o lstart= -p <pid>` 와 파일 수정 시각 비교). 확인하지 못했으면 "확인 필요"로 적는다.
5. **판정.** 네 기준(테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수)을 하나씩 판정한다. 하나라도 미충족이면 반려, 모두 충족인데 "확인 필요"가 남아 있으면 보류, 그 밖에는 승인. 경고를 남긴 채 승인하면 경고마다 "조치 예정" 또는 "보류 사유"를 한 줄 적는다.
6. **되돌리기.** 리뷰 결과를 만든 세션에 넘긴다. 만든 세션은 이슈마다 수용 · 기각을 사람과 정한 뒤 수용한 것만 고치고, 다시 2번부터 돈다.

## 5. 출력 형식

```
판정: 승인 | 반려 | 보류

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 항목 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
```

- 이슈 한 건은 심각도(치명 / 경고 / 제안) · `파일:줄번호` · 근거 · 수정 방향 네 항목을 모두 채운다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 따로 적는다.

## 6. 판정 기준 (v1)

항목 원문은 `templates/approval-checklist.md` v1 에 있다. 여기에는 판정이 갈리는 지점만 적는다.

- 테스트 통과: 새 public 서비스 메서드마다 테스트 1개 이상, 새 엔드포인트마다 `@WebMvcTest` 1개 이상이 있는가? 기존 메서드에 추가한 분기를 지나는 테스트가 없으면 경고다.
- 치명 이슈: 체크리스트 2절 목록(비밀값 · 데이터 손실 · 노출 · 개인정보 · SQL 조립 · 장애 유발 · 보호 대상)에 하나라도 해당하는가? 해당하면 반려다.
- 요청 범위: 요청과 무관한 파일이 3개 이상이거나, 다른 도메인 패키지 · 다른 모듈 문서가 섞였는가? 그렇다면 반려다. 같은 도메인 안의 오타 · 포맷 1~2개는 경고다.
- 컨벤션: 체크리스트 4절의 반려 대상이 하나라도 있는가? 있으면 반려다. 경고 · 제안 대상은 기존 코드의 같은 패턴(`파일:줄번호`)을 근거로 낮추거나 반박할 수 있다.

## 7. 하지 말 것

- 리뷰 세션은 코드를 수정하지 않는다. 보고만 한다.
- 테스트를 실행하지 않고 "통과"라고 쓰지 않는다. 실행할 수 없었으면(서버 꺼짐, 의존성 미설치) 그 사실을 적고 사람에게 기동을 요청한다. 이때 판정은 보류다.
- 요청 범위를 모르는 상태에서 "범위 이탈 없음"을 충족으로 표시하지 않는다.
- 이슈 0건이 나오면 "경고 · 제안 수준까지 다시 봐 달라"고 한 번 더 요청한다. 0건은 결과일 수도, 안 본 것일 수도 있다.
